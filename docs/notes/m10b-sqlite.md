# M10b SQLite：表设计器、导入、比对、模型、迁移、规范检查

M10a 见 `m10a-sqlite.md`。2026-11-05 与用户确认按推荐方案直接做。M10a 的拦截（`later.rs`、前端置灰）已全部去掉。

## 表设计器

- `ALTER TABLE` 只做：加列、删列、改列名、索引增删（索引改名是删了重建）。其余改动（改类型、可空、默认值、约束、列顺序，以及不能直接加的列：非空没有默认值、默认值不是常量、生成列、自增）都改为重建表，原因写在预览里（`sqlite.design.*`）。
- 自增列必须是单列主键，写成 `INTEGER PRIMARY KEY AUTOINCREMENT`；其他整数列按宽度写 `INT`、`BIGINT`（单列 `INTEGER` 主键会成为 rowid 的别名，读回就成了自增）。
- 约束写在建表语句里；外键的 REFERENCES 只写表名；没有注释（`DesignCaps.comments` 为假，界面不显示注释）；没有索引方法。
- 整个改动在一个事务中执行，失败全部回滚。开始事务前执行 `PRAGMA foreign_keys = OFF`（`Dialect::design_prelude`；事务中改不了）。
- 重建（官方文档的做法）：建带全部约束的新表 → 复制（不套 CAST，按列的亲和性转换）→ 核对行数 → 删旧表 → `PRAGMA legacy_alter_table = ON` 下把新表改回原名 → 建索引、触发器 → `PRAGMA foreign_key_check` 核对外键（新的重建步骤 `ForeignKeyCheck`，不通过即失败回滚）。
  - 实测（Python 自带的 3.50.4）：不开 legacy_alter_table 时，引用旧表的视图会让改名失败（`error in view …: no such table`）；外键开着时删旧表会触发子表的 ON DELETE CASCADE。
  - 其他表的外键按列名引用本表：被引用的列删掉或改名时拒绝重建。引用本表的视图列在警告里（按名字匹配，可能多报）。
- 元数据：新增 `referencing_keys`、`dependent_views`；rowid 自增列读成不可空。

## 导入、比对、模型、规范检查

- 导入按主键更新用 `INSERT … ON CONFLICT (…) DO UPDATE SET … = excluded.…`（3.24 起），与 PG 共用一条路径，方言代码没改。
- 比对、模型（反向生成、同步到库）复用设计器的 DDL，实测通过。
- 规范检查：新增 `lint_tables`（没有引擎、字符集、行数估计）；表注释、列注释两条规则对 SQLite 不适用。

## 迁移

- SQLite 作源：迁出去时主键列一律不可空（SQLite 的非 rowid 主键在目录里报可空）。文本日期等由已有的按目标类型转换处理。
- SQLite 作目标：
  - 唯一、检查、外键写在建表语句里，不再 ALTER 添加；"只建缺的"时缺的唯一约束建成唯一索引，检查约束、外键建不了，跳过。
  - 写入连接也先关闭外键（表并行迁移，子表可能先于父表写入；源数据本身满足外键）。
  - 不迁注释；长文本、二进制列可以做键、建索引（不算大字段）。
- 没有序列。

## 已知局限

- SQLite 的 TEXT 列做键迁到 MySQL、Oracle 等时，目标的长文本不能做键，主键不迁并提示（按原有规则）；没有自动改成 VARCHAR。
- 引用本表的视图按表名在视图文本里匹配，可能多报。
- 迁到 SQLite 时，日期时间的默认值写成 CURRENT_TIMESTAMP、CURRENT_DATE、CURRENT_TIME（UTC 文本）；日期时间类型照写精度（`DATETIME(3)`），读回结构一致。
